# Security Policy

## Supported versions

Veneer is in early development. Security fixes are applied to the latest release and the `main` branch only.

| Version | Supported |
| --- | --- |
| latest release | Yes |
| `main` | Yes |
| older releases | No |

## Reporting a vulnerability

**Do not open a public issue for security problems.**

Report vulnerabilities privately through GitHub's private vulnerability reporting:

**https://github.com/LLCForge/Veneer/security/advisories/new**

Please include:

- affected version or commit
- a description of the issue and its impact
- steps or a minimal proof of concept to reproduce it
- any suggested fix, if you have one

## What to expect

| Step | Target time |
| --- | --- |
| Acknowledgement of your report | within 3 business days |
| Initial assessment and severity | within 7 days |
| Fix or mitigation for high/critical issues | within 30 days |
| Public advisory | after a fix is released |

We will keep you informed throughout and credit you in the advisory unless you ask to stay anonymous.

## Scope

In scope:

- memory safety or panics reachable from untrusted input in the Rust core
- code injection through generated init scripts (for example, profile values that escape the script's string context)
- malicious or tampered data in the shipped dataset
- supply-chain issues in the build, release or publishing pipeline (crates.io, npm)
- WASM bindings exposing more than the documented API

Out of scope:

- a specific website detecting a Veneer profile — that is a fingerprint-quality issue; open a regular issue
- vulnerabilities in Playwright, Puppeteer, browsers or other third-party projects — report those upstream
- issues requiring a compromised local machine or developer environment

## Security practices in this project

- `#![forbid(unsafe_code)]` in every crate except `veneer-ffi`, where `unsafe` is limited to reading C arguments and freeing returned strings, each with a SAFETY comment; panics are caught before they cross the C boundary.
- Init scripts are generated by serializing profile data with `serde_json`, never by string concatenation of raw values.
- The dataset is embedded in the binary at build time. Veneer makes no network calls at runtime.
- CI runs `cargo deny` (advisories, licenses, sources); builds fail on known vulnerabilities.
- The local server binds to 127.0.0.1 by default and refuses other addresses without a token; it sends a strict CSP and limits body size and concurrency.
- The `/contribute` page builds reports in the visitor's browser from an allow-list of hardware fields and sends nothing anywhere.
- Releases will be built in CI from tagged commits and published with npm provenance.

## Safe harbor

We will not pursue legal action against researchers who act in good faith, follow this policy, avoid privacy violations and service disruption, and give us reasonable time to fix an issue before disclosure.
